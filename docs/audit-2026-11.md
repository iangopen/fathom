# Fathom audit — November 2026

Read-only audit, 2026-11-16, on macOS (Darwin 25.6.0, arm64), Node v25.8.2,
`NODE_OPTIONS` unset, at commit `a79bb61`. No app code, data or config was
changed. Scratch scripts (bank checks, ledger simulation, axe, Lighthouse,
offline test) ran from a temp folder outside the repo, against the repo's
own modules bundled with its own esbuild.

## Summary

The app is healthy where it matters most. The baseline is unchanged from
October (18 files / 1171 tests, build clean). All 320 questions pass the
mechanical checks: one correct option each, no duplicate options, a valid
citation or topic label, and only COLREGs rule numbers and subparagraphs that
exist. A hand check of a 40-question sample (28 COLREGs-governed) against the
Rules and 33 CFR 83 found **no wrong answers**. It found **2 explanation
errors (5%)**: a wrong subparagraph and a misstated hierarchy. The existing
leak, credit and accessibility guards pass. Lighthouse mobile scores the hub
94–99 for performance and 100 for accessibility and best practices. Every
external link returns 200.

There are two **high** findings, both proved:
1. **History on the seven dropped day-shape ids is orphaned** (F-01). It is
   still stored, but no bar or weak-spot list reads it. A crew member at 25%
   on Day shapes reads 100% after one right answer, and their seven weakest
   items drop off "What you are missing".
2. **The installable PWA does not work offline** (F-02). `sw.js` is a
   pass-through, so an installed Fathom at a waterfront with no signal shows
   "This site can't be reached".

The **medium** findings: real-browser colour-contrast failures that jsdom
could not see (F-03); missing `main` / `h1` landmarks (F-04); the
correct-option-is-longest hint (F-05); the two content errors (F-06); a
Feedback button that still points at the placeholder (F-07); no schema
version on the progress ledger (F-08); silent ledger loss paths (F-09); and
a high-severity dev-server advisory in Vite 6.4.2 (F-10). The rest are low:
dependency majors, CI Node, bundle split, dead code, and CLAUDE.md drift.

### F-01 · high · Saved progress — history on dropped ids is orphaned
**Evidence.** The ledger (`src/lib/progress.ts`, key
`nauticalmaster:charttable:progress`) keeps items by question id. ds-02, 05,
06, 09, 11, 14 and 15 were dropped on 2026-10-09 (commit `0816455`), and
per-item records have existed since 2026-08-30 (`01f7de8`), so real crew
ledgers hold them. `cardMasteryPct` (`src/lib/syllabus.ts:488`) reads only the
items of `itemsForCategory`, and `weakSpots` (`progress.ts`) reads only the ids
it is given. The category tally falls back only when *none* of a card's
items has a record. I ran a simulation with the app's own `progress.ts` and
`syllabus.ts` against a stubbed localStorage:

```
day-shapes card id: shapes
A stored items kept after read: 9 / 9
A category tally: { answered: 34, correct: 13, ... } -> masteryPct(cat tally) = 38
A card bar cardMasteryPct = 100 (from items in deck only)
A overallPct (hub) = 38  totalAnswered = 34
A weakSpots on card: []
A dropped ids still on any card? []
B card bar = 25  (fallback to tally 25%?)  weakSpots: []
B after 1 correct answer on ds-01: card bar = 100  overall = 28  orphan items still stored = 7
C no-items ledger: bar = 60  days = []
```
(A: 7 dropped ids at 1/4 each, plus ds-01 and ds-04 answered right. B: only
dropped ids answered.)

**Impact.** Nothing is deleted, but a crew member's Day shapes history
effectively disappears. The card bar jumps from 25% to 100% on one answer,
the hub's overall figure disagrees with the card (28% vs 100%), and the seven
questions they were missing no longer appear in "What you are missing", so a
weak-spot run will not drill them. The dropped ids were copies of vt-01 to
vt-05, ds-04 and ds-01 (CLAUDE.md, "no drawing shows its own answer"), so a
one-time id alias map would carry the history over intact.
**Effort.** M. Add an alias map applied in `coerce()` (merging tallies),
plus a ledger test, plus F-08's version field so it runs once.

### F-02 · high · PWA / offline — installable, not offline
**Evidence.** `public/sw.js` only does `event.respondWith(fetch(event.request))`.
Chrome DevTools Protocol on `npm run preview`:
```
installability errors: []
manifest url: http://localhost:4173/fathom/manifest.json errors: []
```
A real offline test (a private preview server killed after the page loaded,
because Puppeteer's offline emulation does not reach service-worker fetches):
```
online: SW controls page: true
server down: reload status undefined app rendered: false | body text: This site can’t be reached
```
**Impact.** Crew can install Fathom to the home screen, and it then fails
exactly where they study: on the dock or the water, with no signal, at a
regatta. Progress is local, so nothing else stops offline use.
**Effort.** M. Precache the hashed build assets and the 21 photos (about
1.4 MB) with a versioned cache and a cache-first fetch. This needs a
build-time asset list. vite.config.ts is frozen, so it would need a
post-build script or explicit authorization.

### F-03 · medium · Accessibility — colour contrast in a real browser
**Evidence.** axe-core 4.10 was injected into `npm run preview` in headless
Chrome. Covered: hub, photo question unanswered and answered, a lights
question with Describe open, compass practice, Settings and About, each in
light and dark, plus hub, photo and lights at 375px (20 runs). The
`color-contrast` violations:
```
.ct-instrument-label :: contrast 4.08 (fg #8d773e on #0a1929, 9px). Expected 4.5:1
.text-[10px]         :: contrast 3.72 (fg #64748b on #0a1929, 10px). Expected 4.5:1
Settings chip button :: contrast 3.73 (fg #ece1c8 on #8a6d3b, 10.5px). Expected 4.5:1   (light only)
```
Per view: photo, lights and compass carry 1–2 contrast violations in both
themes; Settings has 1 in light. The sources are `ChartFrame.tsx:145-146`
(`color: rgba(212,169,74,0.65)`) and the literal `text-[10px] text-slate-500`
in 13 diagram components (Light, Buoy, Distress, PFD, CompassRose…).
About alone also carries 118 incomplete (unjudgeable) contrast nodes. No
horizontal scroll at 375px in any view.
**Impact.** Diagram captions ("BOW", "STBD"), the panel kicker and the photo
credit are hard to read for low-vision crew, especially at the night-helm
default.
**Effort.** S. Raise the label alpha, and swap `text-slate-500` for
`text-slate-400` on the navy panel.

### F-04 · medium · Accessibility — landmarks and headings
**Evidence.** The same axe runs report `landmark-one-main` (all 20 runs),
`region` (1–12 nodes) and `page-has-heading-one` (every view but Settings and
About). The prompt is an `h2` (`colregs/index.tsx` ~1035), and the only `h1`
is the results heading.
**Impact.** Screen-reader users cannot jump to main content or find the
question by heading level 1. This is not caught today because the jsdom axe
run evaluates fragments.
**Effort.** S. Use `<main>` in ChartFrame, plus one `h1` per screen.

### F-05 · medium · Answer leaks — option length
**Evidence.** A scratch check over the bank:
```
correctIsUniquelyLongest: 149 / 320
correctAtLeast1_5xLongestDistractor: 54
  (pfd-types 10, distress-signals 8, deck-seamanship 6, signal-flags 5, ...)
promptEchoInCorrectOnly: 4  [by-10, di-04, di-07, di-22]
```
With four options, chance is about 25%. di-07's correct option repeats the
prompt's five content words verbatim. The other routes were checked and are
clean: option order is shuffled per draw (`presentationOrder`,
`colregs/index.tsx:402`; `optionOrder.test.ts` passes); the explanation and
citation render only under `reveal` (`ScenarioCard.tsx:148`); routes are
React state with no URL; localStorage holds only tallies keyed by id; the CSV
export (`App.tsx:80-101`) holds category counts only. The guards pass:
```
$ npx vitest run answerA11y photoCredit imageCredits describeToggle optionOrder
 Test Files  5 passed (5)
      Tests  45 passed (45)
```
The whole bank with `correctAnswer` ships in the client bundle (inherent to
a static app, and readable in DevTools). Noted, not a finding.
**Impact.** A test-wise crew member can score well above their knowledge by
picking the longest answer, which inflates mastery and the pass verdict.
**Effort.** M. Rebalance distractor length (or trim the correct options) in
the worst categories, then add a guard (for example, no correct option
≥1.5× the longest distractor).

### F-06 · medium · Content — sample error rate 5% (2/40)
**Method.** Mechanical check of all 320: one exact `correctAnswer` match, no
duplicate options (case-insensitive), the citation at the start (`Rule N(x)(y)`
/ `Annex N` for governed questions, a TOPIC_LABEL otherwise), every rule
number 1–38, and every subparagraph letter valid for its rule. Result:
`"issues": []`. Then a seeded random sample (seed 20261116) of 28 governed
and 12 other questions was hand-checked against the Navigation Rules
(International / 33 CFR 83): di-02, di-14, vh-13, nl-03, vh-10, di-15, ss-05,
nl-14, ss-04, vt-02, di-07, vt-04, vh-03, ss-02, nl-23, ss-13, di-12, nl-27,
vt-05, ds-01, di-18, ss-06, di-10, ds-04, nl-19, ds-03, vh-05, ss-11, by-28,
dk-25, dk-24, ti-02, by-06, cs-07, wx-17, dk-02, fs-04, by-16, by-01, pf-28.
All 40 correct answers are right. Two explanations are wrong:

1. **vt-04** (`constants.ts:1298`) cites *Rule 26(b)(i)* for the two cones.
   26(b)(i) is the trawler's green-over-white **lights**. The shape is
   **26(b)(ii)** (trawling) or **26(c)(i)** (other fishing). It also says
   26(c)(ii) adds "a cone pointing towards outlying gear". The rule says a
   cone **apex upwards**, in the direction of the gear.
2. **vh-10** (`constants.ts:941`) gives the hierarchy as "NUC > RAM > CBD >
   Fishing…". Rule 18 does not rank NUC above RAM: both sit together in
   18(a)(i)–(ii) and (b)(i)–(ii). CBD is an "avoid impeding" duty under 18(d),
   not a rung between them, and the explanation drops WIG craft (18(f)).

Neither pattern repeats elsewhere (`grep "26(b)(i)\|NUC >"` matches only
these and nl-14, which is right). A minor clarity point that is not counted
as an error: dk-02 calls the quarter "a narrower word for the same end" as
the stern. Extrapolated, roughly 10–20 explanations in the bank may carry a
similar slip; the answers themselves looked sound.
**Impact.** Crew who look up the cited rule land on the wrong paragraph. The
judges at the Regatta and the Rendezvous will expect the right citation.
**Effort.** S for the two fixes. M for a full pass over the governed
questions.

### F-07 · medium · External services — Feedback goes nowhere

### F-08 · medium · Saved progress — no schema version
**Evidence.** `Progress` is `{cats, items, days}` with no `version`
(`progress.ts`). `coerce()` copes by shape-sniffing (the pre-per-item ledger
reads back with empty items: simulation C above).
**Impact.** No reliable "run this migration once" hook, which F-01 needs, as
does any future id change.
**Effort.** S.

### F-09 · medium · Saved progress — silent loss paths
**Evidence.** From the simulation:
```
D after a write, stored: {"cats":{"x":{"answered":2,"correct":2,...}},"items":{},"days":["2026-10-05"]}
   (the malformed 'shapes' entry, last:null, was dropped by coerce() and the next write made it permanent)
E corrupt json -> {"cats":{},"items":{},"days":[]}   (next answer overwrites the whole raw ledger)
F quota: returned answered 1 but stored unchanged; no user notice
```
`recordAnswer` is also read-modify-write with no cross-tab coordination, so
two tabs interleave and the last writer wins.
**Impact.** These are rare, but each one silently loses a crew member's
history, and there is no backup or import to recover it (see O-03).
**Effort.** S. Keep the raw value under a backup key before overwriting an
unparseable ledger, keep unknown entries rather than dropping them, and
surface write failures.
